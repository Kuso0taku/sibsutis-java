# Задание 14. Ограниченный LRU-кэш

## Реализация

`LruCache<K, V>` построен на двух свойствах `LinkedHashMap`:

1. `accessOrder=true` — при `get`/`put` существующего ключа запись
   переставляется в конец (становится «самой свежей»);
2. переопределенный `removeEldestEntry` — при `size() > capacity`
   выкидывает самую старую запись из начала.

Обе операции O(1) амортизированно, память O(capacity).

## Семантика

| Ситуация                        | Поведение                                                       |
|---------------------------------|-----------------------------------------------------------------|
| `get` существующего ключа       | значение + обновляет недавность (не вытеснится первым)         |
| `put` сверх емкости              | самый старый (по последнему обращению) удаляется                |
| `put` существующего ключа        | обновляет значение, размер не растет                            |
| `get` отсутствующего ключа       | `null` — промах, порядок не меняется                            |
| `null` ключ или значение         | `NullPointerException` сразу, хранение `null` запрещено         |

## Доказательство порядком

Тесты фиксируют два сценария:

1. **Вытеснение без чтений** — A, B, C в емкость 3, ставим D → вытеснен A.
2. **Чтение меняет порядок** — после `get(A)` самым старым становится B,
   поэтому `put(D)` вытесняет B, а A остается.

Это и есть «доказательство порядком вытеснения».

## Стабильность ключей

Ключи сравниваются по `equals/hashCode`, а не по ссылке: `new String("a")`
после `put` находится по другому объекту с тем же значением. Как и в task10,
ключ должен быть согласованным — мутабельные ключи ломали бы кэш.
