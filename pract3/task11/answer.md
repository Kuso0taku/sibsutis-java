# Равенство в иерархии

## Нарушение

`Point.equals` принимает любой `Point` (включая `ColoredPoint`), а
`ColoredPoint.equals` — только `ColoredPoint`. Отсюда `p.equals(cp) == true`,
но `cp.equals(p) == false`: равенство несимметрично, `HashSet` ведёт себя
непредсказуемо.

## Исправление 1: strict class equality

`getClass() != o.getClass()` — объекты равны только своего класса.
Симметрия восстановлена, но подкласс с новым полем автоматически перестаёт
быть равен родителю, и каждый новый подтип требует своего equals.

## Исправление 2: композиция цвета

Цвет не наследуется, а оборачивается: `Colored<PlainPoint>(point, "red")`.
`equals` определяет record — симметричный, транзитивный, без иерархии.

## Почему final value class проще

Расширяемая equality-иерархия требует от каждого подкласса переписывать
`equals`/`hashCode` и помнить о родительских полях — легко потерять
симметричность или транзитивность. Финальный value-класс (record) не даёт
наследоваться: контракт равенства зафиксирован один раз и не может быть
сломан подклассом. Цена — отказ от иерархии, но для value-типов её и не нужно.
